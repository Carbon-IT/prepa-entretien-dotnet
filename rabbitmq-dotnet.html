Niveau 1

Notions de base

Ces notions suffisent pour publier et consommer des messages de façon correcte. Elles expliquent le modèle AMQP, le client .NET, l'acquittement et le prefetch.

Rôle d'un broker de messages

Un service envoie un message au broker. Le broker garde le message. Un autre service lit le message plus tard. Les deux services ne se connaissent pas.

Couplage

Découplage

Le producteur ne connaît pas les consommateurs. Vous ajoutez un consommateur sans modifier le producteur. Un consommateur arrêté ne bloque pas le producteur.

Charge

Lissage de charge

Un pic de 5 000 commandes par minute arrive. La file garde les messages. Les consommateurs traitent les messages à leur vitesse. La base de données ne reçoit pas le pic.

Fiabilité

Traitement différé et nouvel essai

Un service partenaire est indisponible. Le message reste dans la file. Le consommateur fait un nouvel essai plus tard. Le client HTTP a déjà reçu sa réponse.

À retenir. Un broker transforme un appel synchrone en échange asynchrone. Le producteur ne connaît pas le résultat du traitement. Utilisez un broker quand le producteur n'a pas besoin de la réponse tout de suite.

Coût. Un broker ajoute un composant à exploiter. Il ajoute aussi de la cohérence à terme : les données des services ne sont pas à jour au même instant. Les messages peuvent arriver deux fois ou dans un ordre différent.

Connexion, channel et client .NET

Le package RabbitMQ.Client version 7 a une API entièrement async. Les exemples suivants utilisent cette version.

Connexion

  • Une connexion TCP, avec TLS et authentification. La création prend plusieurs allers-retours réseau.
  • Créez une connexion par application (ou une pour publier et une pour consommer). Gardez-la pendant toute la vie du process.
  • Le broker affiche le nom donné par ClientProvidedName. Ce nom aide au diagnostic.

Channel

  • Une connexion logique dans la connexion TCP. Une connexion porte beaucoup de channels.
  • Un channel n'est pas fait pour un usage concurrent. Ne partagez pas un channel entre plusieurs publications simultanées.
  • Une erreur de protocole ferme le channel, pas la connexion. Exemple : déclarer une file existante avec d'autres arguments.

QCM : notions de base

Niveau 2

Notions avancées

Ces notions rendent la messagerie fiable : confirmation de publication, livraison au moins une fois, nouvel essai, cohérence avec la base de données, hébergement du consommateur et traces.

Publisher confirms

Sans confirmation, le producteur ne sait pas si le broker a reçu le message. Avec les publisher confirms, le broker envoie un ack quand le message est en sécurité.

Type de fileMoment de l'ack du broker
Message non routable, sans mandatoryImmédiatement. Le message est perdu, mais le broker confirme quand même.
Classic durable, message persistantAprès l'écriture sur disque (fsync groupé).
Quorum queueAprès l'écriture sur une majorité de nœuds.

Débit. Attendre chaque confirmation un par un limite le débit à un message par aller-retour. Pour un lot, lancez plusieurs publications, puis attendez les Tasks avec Task.WhenAll. Limitez le nombre de publications en cours (par exemple 100 à 1 000).

Piège : mandatory. Un ack signifie « le broker a pris le message ». Il ne signifie pas « une file a reçu le message ». Sans mandatory: true ni alternate-exchange, un message sans binding est confirmé, puis supprimé.

Garanties de livraison et idempotence

Un réseau peut couper une connexion à tout moment. Le broker ne peut donc pas garantir « exactement une fois ». Il garantit « au plus une fois » ou « au moins une fois ».

At-most-once

Au plus une fois

autoAck: true, pas de confirms. Le message peut être perdu. Il n'arrive jamais deux fois. Acceptable pour une métrique ou un cache à rafraîchir.

At-least-once

Au moins une fois

Confirms côté producteur, ack manuel après le traitement. Aucun message n'est perdu. Un message peut arriver deux fois. C'est le choix par défaut.

Effectively-once

Effet unique

At-least-once + consommateur idempotent. Le message arrive deux fois, mais l'effet a lieu une fois. Vous construisez cette garantie dans l'application.

Causes d'un doublon

  • Le consommateur traite le message. La connexion coupe avant l'ack. Le broker livre de nouveau le message (Redelivered = true).
  • Le producteur publie. L'ack du broker est perdu. Le producteur publie de nouveau.
  • Le relais d'outbox publie, puis s'arrête avant de marquer la ligne comme publiée.

Consommateur idempotent avec EF Core

Autres techniques. Une opération naturellement idempotente : UPDATE ... SET Status = 'Paid'. Un upsert sur une clé métier. Une version optimiste sur l'agrégat. La table des messages traités est la solution générale.

Nouvel essai et dead letter : message empoisonné pas à pas

Le consommateur échoue sur un message. Un requeue immédiat crée une boucle. La topologie suivante attend 5 s entre deux essais. Après 3 échecs, le message part dans une file de rebut (parking lot).

Trois files, deux règles de dead letter

FileRôleRègle de dead letter
billingFile principale, liée à l'exchange orders. Le consommateur la lit.Un message refusé part dans billing.wait.
billing.waitSalle d'attente. Aucun consommateur ne la lit.Après 5 s, un message expiré retourne dans billing, et dans aucune autre file.
billing.parkingFile de rebut. Une personne analyse son contenu.Aucune. Les messages y restent.

Qui déplace le message ?

Le consommateur ne cite jamais billing.wait. Il refuse le message, et c'est tout. Le broker lit ensuite la règle de dead letter de la file, puis déplace le message. Une règle de dead letter est comme une redirection de courrier : « tout ce qui est refusé ici part là-bas ».

  1. Le consommateur refuse le message

    BasicNackAsync(requeue: false) retire le message de billing.

  2. Le broker applique la règle de billing

    Il publie le message sur l'exchange par défaut "" avec la clé billing.wait. L'exchange par défaut envoie un message à la file dont le nom est égal à la clé. Le broker ajoute aussi une entrée dans le header x-death.

  3. Le message attend

    Aucun consommateur ne lit billing.wait. Après 5 s, le TTL expire.

  4. Le broker applique la règle de billing.wait

    Il publie le message sur "" avec la clé billing. Le message retourne dans billing, et dans aucune autre file.

  5. Le consommateur fait un nouvel essai

    Au 3e échec, le code ne fait pas de nack. Il publie lui-même le message dans billing.parking, puis fait l'ack de l'original.

Appel dans le catchRésultat
BasicNackAsync(requeue: true)Le message retourne tout de suite dans billing. La règle de dead letter ne s'applique pas. Il n'y a pas d'attente : risque de boucle rapide.
BasicNackAsync(requeue: false)La règle de dead letter de la file s'applique. Le message part dans billing.wait.
requeue: false sans x-dead-letter-exchangeLe broker supprime le message. Il est perdu, sans erreur.

L'exchange par défaut "". Chaque file est liée automatiquement à cet exchange, avec son nom comme clé. Publier sur "" avec la clé billing.parking envoie donc le message dans la file billing.parking, et seulement dans celle-ci. Aucune déclaration d'exchange ni de binding n'est nécessaire. C'est le moyen le plus simple de viser une seule file.

Erreur transitoire ou permanente. Un timeout HTTP est transitoire : un nouvel essai a un sens. Un JSON invalide est permanent : envoyez le message directement dans la file de rebut. Un nouvel essai ne le corrige pas.

Outbox avec EF Core

Outbox (côté producteur)

Le message est écrit dans la même transaction que les données. Un relais le publie ensuite. Résultat : aucun événement perdu, aucun événement fantôme. Les doublons sont possibles : le relais peut publier deux fois.

Inbox (côté consommateur)

Le consommateur enregistre le MessageId dans la même transaction que son traitement. Il ignore un message déjà enregistré. Outbox + Inbox donnent un effet unique de bout en bout.

Consommateur hébergé : BackgroundService et scope DI

Un consommateur vit pendant toute la vie de l'application. Un DbContext est scoped. Créez donc un scope DI par message.

Erreurs fréquentes. Injecter un DbContext dans le constructeur d'un service singleton : le contexte vit pour toujours et grossit. Oublier le try/catch : le message reste unacked jusqu'à la fermeture du channel. Faire un ack avant le traitement : un crash perd le message.

Arrêt propre. À l'arrêt, stoppingToken est annulé. Les messages unacked reviennent dans la file à la fermeture du channel. Un autre pod les traite. Le traitement doit donc rester idempotent.

Traces distribuées : traceparent dans les headers

Une requête HTTP publie un message. Un worker le consomme. Pour voir une seule trace, le contexte de trace doit voyager dans les headers du message.

Côté consommateur. Le consommateur lit traceparent dans ea.BasicProperties.Headers. Il démarre une Activity de type Consumer avec ce parent. Les logs du worker ont alors le même TraceId que la requête HTTP. Avec une outbox, enregistrez aussi traceparent dans la ligne d'outbox.

Quorum queues et Raft pas à pas

Une quorum queue a un leader et des followers, sur trois nœuds dans cet exemple. Le leader écrit chaque opération dans un journal. Une opération est validée quand une majorité de nœuds l'a écrite.

Producteur

Coût. Chaque message est écrit sur disque sur plusieurs nœuds. Une quorum queue utilise plus de disque et de réseau qu'une classic queue. Une file très longue ralentit la récupération d'un nœud. Gardez les files courtes : un consommateur doit suivre le rythme du producteur.

Un stream est un journal append-only répliqué, comme une partition Kafka. Un consommateur lit à partir d'un offset. Les messages ne sont pas supprimés après la lecture.

Flow control et alarmes mémoire ou disque

Le broker protège sa mémoire et son disque. Quand une ressource manque, il ralentit ou bloque les producteurs.

Interne

Credit flow

Chaque processus interne du broker donne un crédit au processus précédent. Une file lente ne donne plus de crédit. Le broker arrête de lire le socket du producteur. La connexion passe à l'état flow. Le producteur ralentit sans erreur.

Mémoire

Alarme mémoire

Seuil : vm_memory_high_watermark, une fraction de la RAM disponible. Au-dessus, le broker bloque toutes les connexions qui publient, sur tout le cluster.

Disque

Alarme disque

Seuil : disk_free_limit. Sous ce seuil d'espace libre, le broker bloque les publications. Les consommateurs continuent à lire et à acquitter.

Effet dans une API. Pendant une alarme, BasicPublishAsync attend. Une requête HTTP qui publie attend aussi. Passez un CancellationToken avec un délai. Une outbox évite ce problème : la requête écrit seulement en base.

Partager une connexion. Le broker bloque une connexion entière. Une connexion qui publie et consomme est bloquée aussi pour les acks. Les consommateurs ne peuvent plus vider les files. Séparez la connexion de publication et la connexion de consommation.

Calcul du prefetch

Le consommateur doit toujours avoir un message prêt. Entre l'ack et l'arrivée du message suivant, il y a un aller-retour réseau. Le prefetch doit couvrir ce temps.

Prefetch minimal conseillé

Débit maximal

Débit avec prefetch 1

Modèle simplifié : débit = min(concurrence / traitement, prefetch / (traitement + aller-retour)). Prefetch conseillé = concurrence × (1 + aller-retour / traitement), arrondi au-dessus.

Règles pratiques. Traitement rapide et réseau lent : grand prefetch (100 à 300). Traitement long (plusieurs secondes) : petit prefetch (1 à concurrence). Un prefetch trop grand garde les messages chez un seul consommateur et augmente la mémoire. Sans BasicQos, le prefetch est illimité.

Channels, concurrence et delivery tags

Le client .NET exécute les callbacks des consommateurs dans un dispatcher. Par défaut, un channel traite un message à la fois.

Delivery tag

  • Le broker numérote les livraisons par channel : 1, 2, 3…
  • Un ack doit utiliser le channel qui a reçu le message. Sur un autre channel, le tag est inconnu. Le broker ferme ce channel avec 406 PRECONDITION_FAILED - unknown delivery tag.
  • Un double ack du même tag provoque la même erreur.
  • multiple: true acquitte tous les tags inférieurs ou égaux. Avec une concurrence supérieure à 1, ce réglage acquitte des messages encore en traitement.

Concurrence et ordre

  • Avec ConsumerDispatchConcurrency = 1, les messages d'un channel sont traités l'un après l'autre.
  • Avec une valeur supérieure, l'ordre de fin des traitements change.
  • Le prefetch doit être au moins égal à la concurrence. Sinon, des slots restent vides.
  • Publication : n'utilisez pas un channel pour plusieurs publications concurrentes. Utilisez un channel par publieur ou un pool de channels.

Code bloquant dans le callback. Le callback ReceivedAsync doit être async de bout en bout. Un .Result dans le callback bloque le dispatcher et un worker du ThreadPool. Voir la page Async et threads .NET.

Heartbeats et reconnexion automatique

Une connexion TCP peut mourir sans fermeture visible : pare-feu, NAT, nœud arrêté. Les heartbeats détectent ce cas. La reconnexion automatique recrée ensuite la connexion.

Réglage ConnectionFactoryDéfautEffet
RequestedHeartbeat60 sLe client et le broker envoient une trame vide si la connexion est inactive. Après environ deux intervalles sans trame, la connexion est considérée comme morte.
AutomaticRecoveryEnabledtrueLe client recrée la connexion et les channels après une coupure réseau.
TopologyRecoveryEnabledtrueLe client déclare de nouveau les exchanges, files, bindings et consommateurs créés par cette connexion.
NetworkRecoveryInterval5 sDélai entre deux tentatives de reconnexion.

Cas non couverts. La première connexion au démarrage n'a pas de reconnexion automatique : prévoyez une boucle avec délai (ou Polly). Une fermeture volontaire par le broker (erreur de protocole, channel fermé par un 406) n'est pas reprise. Les messages unacked au moment de la coupure reviennent en file avec Redelivered = true.

Single active consumer et consistent hash exchange

Deux outils gardent l'ordre avec plusieurs instances de l'application.

Single active consumer

Argument de file x-single-active-consumer = true. Plusieurs consommateurs s'abonnent. Le broker livre les messages à un seul consommateur. Si ce consommateur s'arrête, le broker active le suivant.

Résultat : ordre strict et haute disponibilité. Mais une seule instance travaille.

Consistent hash exchange

Plugin rabbitmq_consistent_hash_exchange, type x-consistent-hash. L'exchange calcule un hash de la routing key (par exemple l'identifiant de commande). Il envoie toujours la même clé vers la même file.

Résultat : ordre par clé, et une file par consommateur. La clé de binding est un poids, pas un motif.

Limite. Ajouter une file déplace une partie des clés vers la nouvelle file. Pendant ce changement, deux messages d'une même clé peuvent être dans deux files. Choisissez le nombre de partitions au départ.

Messages empoisonnés et x-delivery-limit

Un message fait planter le consommateur à chaque essai. Avec un requeue, il revient en tête de file. Il bloque alors les autres messages et utilise le CPU sans fin.

FileComportement
ClassicAucun compteur. BasicNack(requeue: true) crée une boucle infinie. Seul indice : Redelivered = true, sans nombre d'essais.
QuorumLe broker compte les retours en file dans le header x-delivery-count. Au-delà de x-delivery-limit, il supprime le message ou l'envoie au DLX. RabbitMQ 4 fixe cette limite à 20 par défaut.

Dead lettering at-least-once. Par défaut, le transfert vers le DLX est at-most-once : une perte est possible si la file cible est indisponible. La stratégie at-least-once des quorum queues garde le message jusqu'à la confirmation de la file cible.

Exploitation. Surveillez la taille des files de rebut avec une alerte. Prévoyez un outil pour relire, corriger et republier les messages. Une file de rebut sans suivi est une perte de données lente.
