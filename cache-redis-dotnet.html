Niveau 1

Notions de base

Ces notions suffisent pour ajouter un cache correct à une API .NET. Elles expliquent le pattern cache-aside, les trois API de cache de .NET, l'expiration et l'utilisation de Redis.

Raisons d'utiliser un cache

Un cache garde une copie d'une donnée près du code qui la lit. Une lecture dans le cache est plus rapide qu'une lecture dans la source. Mais la copie peut être périmée.

Latence

Réponse plus rapide

Mémoire du process : moins de 1 µs. Redis sur le réseau local : environ 0,5 à 1 ms. Requête SQL avec jointures : 5 à 200 ms. Appel à une API partenaire : 50 à 500 ms.

Charge

Moins de travail pour la source

Avec 95 % de hit, la base reçoit 20 fois moins de lectures. La base supporte donc un pic de trafic plus important.

Coût

Fraîcheur des données

Une donnée en cache peut être différente de la source. Pour chaque donnée, définissez la durée de périmé acceptable.

Bons candidats

  • Données lues souvent et modifiées rarement : catalogue, référentiels, configuration.
  • Résultats de calculs coûteux : agrégats, rapports, pages de recherche fréquentes.
  • Réponses d'API externes lentes ou facturées à l'appel.
  • Données de session ou jetons, avec une durée limitée.

Mauvais candidats

  • Données qui doivent être exactes à chaque lecture : solde, stock au moment de la commande.
  • Données lues une seule fois : le taux de hit est proche de 0.
  • Données personnelles sensibles sans chiffrement ni durée courte.
  • Requêtes déjà rapides : le cache ajoute de la complexité sans gain mesurable.

À retenir. Le cache échange de la fraîcheur contre de la vitesse. Mesurez d'abord la latence et la charge. Ajoutez ensuite un cache pour une lecture précise, avec un TTL choisi pour cette donnée.

Pattern cache-aside

Le code de l'application gère le cache. À la lecture, il essaie le cache puis la source. À l'écriture, il modifie la source puis supprime l'entrée du cache. C'est le pattern le plus courant.

Autres patterns

Read-throughLe cache lit lui-même la source en cas de miss. L'application parle seulement au cache.GetOrCreateAsync donne ce comportement côté code.

Refresh-aheadLe cache recharge une entrée populaire avant son expiration.Clés très lues. FusionCache : EagerRefreshThreshold.

Supprimer, ne pas écrire. Après une modification, supprimez la clé. N'écrivez pas la nouvelle valeur dans le cache. Deux écritures concurrentes peuvent arriver dans le cache dans un ordre différent de la base. Le cache garde alors l'ancienne valeur jusqu'au TTL. Une suppression n'a pas ce problème.

Redis avec StackExchange.Redis

Redis est un serveur de structures de données en mémoire. StackExchange.Redis est le client .NET le plus utilisé. IDistributedCache utilise ce client, mais il expose seulement des chaînes d'octets.

Un seul multiplexer. ConnectionMultiplexer est thread-safe et coûteux à créer : connexion TCP, TLS, découverte de la topologie. Créez-en un par application et par serveur Redis. Un multiplexer par requête ouvre des milliers de connexions et sature Redis. abortConnect=false permet au process de démarrer quand Redis est indisponible : le multiplexer se reconnecte en arrière-plan.

Conception des clés et TTL

Redis n'a pas de tables. Toutes les clés sont dans un seul espace par base. Un nom de clé structuré évite les collisions et facilite le diagnostic.

Règles de nommage

  • Préfixe d'application : catalog:. Plusieurs applications partagent souvent le même Redis.
  • Type d'objet et identifiant : catalog:product:42.
  • Version du format : catalog:product:v2:42. Après un changement du DTO, les anciennes valeurs ne sont plus lues. Elles expirent seules.
  • Pas de données brutes de l'utilisateur : une recherche longue ou avec des caractères spéciaux donne une clé imprévisible. Utilisez un hash (SHA-256) du critère.
  • Clé courte : chaque clé utilise de la mémoire. Évitez les clés de plusieurs centaines d'octets.

TTL en Redis

Clé sans TTL. Une clé de cache sans TTL reste en mémoire pour toujours. Redis se remplit. Avec la politique par défaut noeviction, Redis refuse ensuite les écritures. Donnez un TTL à chaque clé de cache.

Simulateur : cache stampede

Une clé très lue expire. Des requêtes arrivent pendant le rechargement. Sans protection, chaque requête trouve un miss et lance la même requête SQL. La base reçoit beaucoup de requêtes identiques. Elle ralentit, et le rechargement dure plus longtemps. Dans ce modèle, la base traite 10 requêtes à la fois sans ralentir.

Limite du coalescing. HybridCache regroupe les appels dans un process. Avec 10 instances, la base reçoit au plus 10 requêtes, une par instance. C'est en général suffisant. TTL et jitter

Après un déploiement ou un vidage de Redis, l'application recharge beaucoup de clés au même moment. Avec le même TTL, toutes ces clés expirent ensemble. La charge sur la base revient par vagues. Un jitter ajoute une variation aléatoire au TTL. Les expirations se répartissent dans le temps.

HybridCache est l'API recommandée depuis .NET 9. Le package fonctionne aussi avec .NET 8. Il remplace le code cache-aside écrit à la main.

Choisissez une durée L1 compatible avec l'écart acceptable. Pour une invalidation immédiate sur toutes les instances, utilisez une bibliothèque avec backplane (FusionCache) ou désactivez L1 pour cette donnée.

Fail-safe, timeouts et Redis indisponible

Le cache doit accélérer l'application. Il ne doit pas la rendre indisponible. Deux questions : que fait l'API si Redis ne répond pas ? Que fait l'API si la base ne répond pas pendant un rechargement ?

Redis indisponible

  • IDistributedCache et IDatabase lèvent une RedisConnectionException ou une RedisTimeoutException.
  • Sans try/catch, chaque requête retourne une erreur 500, même si la base fonctionne.
  • Traitez une erreur de cache comme un miss : journalisez, puis lisez la source.
  • Réduisez syncTimeout/asyncTimeout (5 s par défaut). Un cache qui répond en 5 s n'a plus d'intérêt.

Source indisponible : fail-safe

  • La valeur expire. La factory échoue ou dépasse un délai.
  • Avec le fail-safe, le cache retourne l'ancienne valeur expirée. Il réessaie plus tard.
  • L'utilisateur reçoit une donnée un peu périmée au lieu d'une erreur.
  • FusionCache propose ce mécanisme. HybridCache ne le propose pas.

Disjoncteur. Quand Redis tombe, chaque appel attend le timeout. Un disjoncteur (DistributedCacheCircuitBreakerDuration dans FusionCache, ou Polly) arrête les appels vers Redis pendant une durée courte. L'API fonctionne alors avec L1 et la base, sans attente.

Un verrou distribué empêche deux instances d'exécuter le même travail en même temps. La base du verrou Redis est SET clé jeton NX PX durée. Mais une pause du process peut casser le verrou. Avancez étape par étape.

Redlock. L'algorithme Redlock prend le verrou sur une majorité de 5 serveurs Redis indépendants. Il protège contre la panne d'un serveur. Notions profondes

Ces notions expliquent le fonctionnement interne de Redis et du client StackExchange.Redis : boucle d'événements, multiplexage, timeouts, persistance, topologie et gestion de la mémoire.

Redis mono-thread : la boucle d'événements

Redis exécute les commandes sur un seul thread. Ce thread prend les commandes l'une après l'autre dans une boucle d'événements (epoll sous Linux). Chaque commande est donc atomique. Aucun verrou n'est nécessaire.

Avantage

Rapide et simple

Les données sont en mémoire. Une commande simple dure environ 1 µs. Un thread traite plus de 100 000 commandes par seconde. Le réseau limite le débit avant le CPU.

Risque

Une commande lente bloque tout

Pendant un KEYS * de 2 secondes, Redis ne traite aucune autre commande. Tous les clients attendent. Les clients .NET reçoivent des timeouts.

Redis 6+

Threads d'I/O

L'option io-threads répartit la lecture et l'écriture sur les sockets entre plusieurs threads. L'exécution des commandes reste sur un seul thread.

Autres threads. Redis utilise aussi des threads de fond : suppression asynchrone (UNLINK, lazyfree), fermeture de fichiers, fsync de l'AOF. La sauvegarde RDB utilise un process enfant (fork). Pour utiliser plusieurs cœurs, déployez plusieurs instances Redis (Cluster).

Simulateur : round-trips, pipelining et multiplexage

Le code lit N clés. Chaque commande dure quelques µs sur le serveur. Le réseau ajoute un RTT par aller-retour. En séquentiel, le client attend chaque réponse avant d'envoyer la commande suivante. En pipeline, le client envoie toutes les commandes, puis lit toutes les réponses.

Multiplexage dans StackExchange.Redis

Le multiplexer utilise une seule connexion TCP pour toutes les commandes de tous les threads. Il écrit les commandes dans la socket dans l'ordre d'arrivée. Redis répond dans le même ordre. Le multiplexer associe chaque réponse à la Task en attente. Le pipelining est donc automatique : plusieurs requêtes HTTP concurrentes partagent les allers-retours.

Blocage en tête de file. Les réponses arrivent dans l'ordre. Une valeur de 20 Mo occupe la connexion pendant son transfert (environ 160 ms à 1 Gbit/s). Toutes les commandes envoyées après elle attendent, même un petit GET. Gardez les valeurs petites (moins de 100 Ko). Pour les grosses valeurs, utilisez un stockage objet et gardez seulement la référence dans Redis.

Commandes O(N) et big keys

Une commande O(1) dure le même temps pour 10 clés ou 10 millions de clés. Une commande O(N) dure plus longtemps quand les données grandissent. Sur un serveur mono-thread, elle bloque tous les clients.

Réplication, Sentinel et Cluster

      
Un serveur Redis seul est un point de défaillance unique. Trois topologies existent.

      

        
Réplication
Primaire et réplicas
Le primaire envoie ses écritures aux réplicas de façon asynchrone. Une écriture confirmée peut être perdue si le primaire tombe. WAIT attend la copie sur N réplicas, mais ne garantit pas la cohérence forte.

        
Sentinel
Bascule automatique
Des processus Sentinel surveillent le primaire. Si le primaire tombe, ils promeuvent un réplica. Le client demande l'adresse du primaire à Sentinel (serviceName= dans la configuration).

        
Cluster
Partitionnement
Les clés sont réparties sur plusieurs primaires, avec 16 384 hash slots. Chaque primaire a ses réplicas. Le client calcule le slot de chaque clé et envoie la commande au bon nœud.

      

      
Calculer le hash slot d'une clé

      
Slot = CRC16(clé) mod 16384. Si la clé contient {…}, seul le texte entre accolades est haché : c'est un hash tag. Les commandes multi-clés (MGET, transactions, scripts Lua) exigent des clés du même slot. Sinon, Redis répond CROSSSLOT.

      

        

          

          

        

        
Exemples :

        

        

      

      
MOVED et ASK. Si le client envoie une commande au mauvais nœud, Redis répond MOVED slot adresse. StackExchange.Redis met à jour sa carte des slots et renvoie la commande. Pendant une migration de slot, Redis répond ASK pour une clé déjà déplacée. Le client suit ces redirections sans code applicatif. Attention : un hash tag trop utilisé place beaucoup de clés sur un seul nœud (hot shard).

    


    

      
Atomicité : MULTI/EXEC et scripts Lua

      
Chaque commande Redis est atomique. Une suite de commandes ne l'est pas. Deux mécanismes groupent des commandes.

      

        

          
Transaction avec conditions


          
MULTI/EXEC exécute les commandes en bloc. Il n'y a pas de rollback : si une commande échoue, les autres s'exécutent quand même. Les commandes du bloc ne peuvent pas lire le résultat d'une commande précédente.

        

        

          
Script Lua


          
Le script s'exécute en entier, sans autre commande au milieu. Il peut lire puis écrire. Il bloque le serveur pendant son exécution. Passez toutes les clés dans KEYS : Redis Cluster en a besoin pour router le script.

        

      

    


    

      
Éviction : LRU approximé par échantillonnage

      
Un LRU exact demande une liste chaînée de toutes les clés, mise à jour à chaque lecture. Redis évite ce coût. Chaque clé garde l'heure de son dernier accès sur 24 bits. Pour évincer, Redis tire au hasard maxmemory-samples clés (5 par défaut) et supprime la plus ancienne. Un pool d'éviction garde les meilleurs candidats entre deux tirages.

Calcul sans le pool d'éviction : le rang est 0 % pour la clé la plus récente et 100 % pour la plus ancienne. Le pool améliore le résultat réel. Avec 10 échantillons, le résultat est très proche d'un LRU exact. Le LFU utilise un compteur logarithmique de 8 bits par clé. Ce compteur diminue avec le temps (lfu-decay-time).

    


    

      
Mémoire : surcoût et fragmentation

      
La mémoire utilisée par Redis est plus grande que la taille des valeurs. Chaque clé a un surcoût. L'allocateur (jemalloc) laisse des trous après les suppressions.


      

        

          
Réduire la mémoire

          
    
            
  • Surcoût d'une clé : environ 50 à 70 octets en plus de la clé et de la valeur.
    • 
            
  • Petits hash et sorted sets : encodage compact (listpack) sous les seuils hash-max-listpack-entries (128) et hash-max-listpack-value (64 octets).
    • 
            
  • Regrouper beaucoup de petites valeurs dans des hash peut réduire fortement la mémoire.
    • 
            
  • Compresser les grosses valeurs côté client.
    • 
          

        

        

          
Fragmentation

          
    
            
  • Ratio supérieur à 1,5 : beaucoup de mémoire libre non réutilisée, souvent après des suppressions massives.
    • 
            
  • activedefrag yes : Redis déplace les données en arrière-plan pour combler les trous.
    • 
            
  • Ratio inférieur à 1 : le système a déplacé une partie de Redis dans le swap. La latence devient très mauvaise.
    • 
            
  • Réglez maxmemory sous la mémoire du conteneur : gardez de la marge pour la fragmentation, les buffers clients et le fork.
