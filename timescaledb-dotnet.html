Notions de base

Ces notions suffisent pour créer une hypertable, l'utiliser avec EF Core et éviter les erreurs fréquentes.

Séries temporelles et TimescaleDB

Une série temporelle est une suite de mesures horodatées. Exemples : température d'un capteur, prix d'un actif, latence d'une API, consommation d'énergie.

Écriture

Ajout, presque jamais de mise à jour

Les mesures arrivent en continu. Le volume est grand : 1 000 capteurs à 1 mesure par seconde donnent 86 millions de lignes par jour.

Lecture

Plages de temps et agrégats

Les requêtes lisent une plage récente. Elles calculent des moyennes par heure ou par jour. Elles lisent rarement une ligne seule.

Cycle de vie

Les données vieillissent

Les données récentes sont lues souvent. Les données anciennes sont compressées, agrégées puis supprimées.

TimescaleDB est une extension de PostgreSQL. Ce n'est pas une autre base de données. Vous gardez SQL, les jointures, les transactions, les index et les outils PostgreSQL. Côté .NET, vous gardez Npgsql et le provider EF Core Npgsql.EntityFrameworkCore.PostgreSQL.

Requête sur les dernières 24 hLe planner parcourt un grand index.Le planner exclut les chunks hors de la plage.
Supprimer les données de plus de 90 joursDELETE de millions de lignes, WAL, puis VACUUM.drop_chunks supprime des tables entières. L'opération est presque instantanée.

À retenir. TimescaleDB reste PostgreSQL. Une hypertable s'utilise comme une table. EF Core la lit et l'écrit comme une table. Les fonctions propres à Timescale (time_bucket, compression, continuous aggregates) demandent du SQL ou un mapping explicite.

Hypertable et chunks

Créez d'abord une table PostgreSQL normale. Transformez-la ensuite en hypertable. Les insertions créent les chunks automatiquement.

Ce que fait create_hypertable

  • La table measurements devient la table parente. Elle ne contient plus de lignes.
  • Chaque insertion va dans le chunk de son intervalle. TimescaleDB crée le chunk s'il n'existe pas.
  • Les chunks sont dans le schéma _timescaledb_internal. Exemple : _hyper_1_42_chunk.
  • Chaque chunk a une contrainte CHECK sur sa plage de temps. Le planner utilise cette contrainte pour exclure le chunk.
  • TimescaleDB crée par défaut un index sur time DESC.

Règle de la clé unique

Une contrainte unique ou une clé primaire doit contenir la colonne de partition. Chaque chunk vérifie l'unicité localement. Sans la colonne de temps, le moteur devrait vérifier tous les chunks à chaque insertion.

Erreur fréquente. Une entité EF avec int Id en clé auto-incrémentée donne PRIMARY KEY (id). L'appel à create_hypertable échoue alors. Utilisez une clé composite qui contient le temps. Voir Modèle EF Core.

time_bucket : regrouper par intervalle

time_bucket(largeur, time) arrondit chaque horodatage au début de son intervalle. C'est un date_trunc avec une largeur libre : 5 minutes, 15 minutes, 3 heures.

Largeur du bucket

Données : 24 mesures du capteur 42, une toutes les 5 minutes, de 08:00 à 09:55 UTC.

Alignement

Les buckets sont alignés sur une origine fixe. Pour une largeur en jours, l'origine par défaut est un lundi (2000-01-03). Un bucket de 1 jour commence donc à minuit UTC. Pour un fuseau horaire, utilisez la variante time_bucket('1 day', time, 'Europe/Paris').

Bucket et exclusion

Utilisez time_bucket dans le SELECT et le GROUP BY. Filtrez sur la colonne time brute dans le WHERE. Un WHERE time_bucket(...) = ... empêche l'exclusion de chunks.

Modèle EF Core avec Npgsql

EF Core ne connaît pas les hypertables. Pour EF Core, measurements est une table normale. Vous configurez la clé, les types et les index. Une migration crée ensuite l'hypertable avec du SQL.

ChoixConséquence
HasKey(m => new { m.DeviceId, m.Time })Clé composite. Elle contient le temps : create_hypertable l'accepte. EF peut suivre, modifier et supprimer une ligne. Deux mesures d'un même capteur au même instant sont refusées.
HasNoKey()Pas de clé primaire en base. EF peut lire l'entité, mais SaveChanges refuse de l'insérer. Insérez alors avec COPY ou du SQL.
int Id auto-incrémentéClé sans le temps : create_hypertable échoue. Un Id n'a pas d'intérêt pour une mesure.
Index (device_id, time DESC)La clé primaire le fournit déjà dans cet ordre de colonnes. C'est l'index de la requête « mesures d'un capteur sur une plage ».

Requête LINQ simple. Une requête LINQ sur l'hypertable est traduite en SQL normal. TimescaleDB applique l'exclusion de chunks sans changement côté .NET.

Dates : timestamptz et DateTime UTC

Depuis Npgsql 6, le mapping des dates est strict. Une erreur de Kind lève une exception à l'écriture. C'est voulu : la règle évite les décalages silencieux.

Type .NETType PostgreSQLRègle Npgsql 6 et plus
DateTime, Kind = UtctimestamptzAccepté. C'est le mapping par défaut. La lecture retourne un DateTime avec Kind = Utc.
DateTime, Kind = Local ou UnspecifiedtimestamptzRefusé : ArgumentException à l'écriture.
DateTime, Kind = Unspecifiedtimestamp (sans fuseau)Accepté. Déconseillé pour une colonne de partition : l'heure d'été donne des trous et des doublons.
DateTimeOffsettimestamptzAccepté seulement avec un offset nul. Un offset +01:00 est refusé.

Commutateur legacy. AppContext.SetSwitch("Npgsql.EnableLegacyTimestampBehavior", true) rétablit l'ancien comportement. Ce commutateur masque le problème. Utilisez-le seulement pendant une migration d'un ancien projet.

Insertion en masse : SaveChanges ou COPY

Une série temporelle reçoit beaucoup de lignes. Le change tracker d'EF Core coûte cher pour ce volume. Comparez les méthodes.

Limites de COPY. COPY ne gère pas les conflits : un doublon de clé arrête tout l'import. Pour un upsert, copiez dans une table temporaire, puis exécutez INSERT ... SELECT ... ON CONFLICT DO NOTHING.

Notions avancées

Ces notions gèrent le cycle de vie des données : compression, agrégats continus, rétention. Elles expliquent aussi l'usage de ces objets depuis EF Core.

Compression : segmentby et orderby

La compression transforme un chunk ancien en format colonnes. TimescaleDB regroupe les lignes par lots de 1 000 au plus. Chaque lot devient une ligne avec un tableau compressé par colonne.

segmentby
Valeurs

Un chunk = 1 jour. Chaque capteur envoie 1 mesure par minute (1 440 lignes par capteur et par jour).

Taux de compression

Lots compressés

Lignes décompressées pour device_id = 42

Choisir segmentby

  • La colonne des filtres fréquents : device_id, tenant_id.
  • Cardinalité moyenne : assez de lignes par valeur pour remplir des lots.
  • Pas un identifiant unique : un lot par ligne, la table grossit.

Choisir orderby

  • Par défaut : la colonne de temps, ordre décroissant.
  • TimescaleDB stocke le min et le max de chaque colonne orderby par lot. Un filtre sur le temps saute les lots hors plage.
  • Les valeurs triées se suivent : les deltas sont petits, la compression est meilleure.

Continuous aggregates

Un continuous aggregate est une vue matérialisée de time_bucket. Une policy la rafraîchit. Elle recalcule seulement les buckets modifiés.

Bucket matérialiséCalculé à la requête (real-time)Bucket invalidé, à rafraîchirAbsent du résultat
Buckets
  • materialized_only
  • Watermark (fin de la partie matérialisée)
  • Résultat de SELECT * FROM measurements_hourly

Real-time aggregation. Depuis la version 2.13, une nouvelle vue a materialized_only = true par défaut. La vue retourne seulement les buckets matérialisés. Avec materialized_only = false, la vue ajoute un calcul sur les données brutes après le watermark.

Vue agrégée dans EF Core

Pour EF Core, un continuous aggregate est une vue en lecture seule. Mappez-la en entité sans clé. Créez-la dans une migration avec du SQL.

Transaction. EF Core exécute chaque migration dans une transaction. CREATE MATERIALIZED VIEW ... WITH (timescaledb.continuous) et CALL refresh_continuous_aggregate échouent dans une transaction : « cannot run inside a transaction block ». Passez suppressTransaction: true à mb.Sql.

Snapshot du modèle. ToView indique à EF que l'objet existe déjà. EF ne génère pas de CREATE pour lui. Le ModelSnapshot garde quand même l'entité : les migrations suivantes restent cohérentes.

Rétention : drop_chunks ou DELETE

Supprimer des données anciennes est une opération fréquente. Sur une hypertable, supprimez des chunks entiers, pas des lignes.

1,44 million de lignes par jour. Chunks de 1 jour.

ExecuteDeleteAsync (DELETE)

    drop_chunks

      Granularité. drop_chunks supprime seulement les chunks entièrement plus anciens que la limite. Avec des chunks de 7 jours, des données de 96 jours peuvent rester. Les continuous aggregates gardent leurs buckets si leur fenêtre de rafraîchissement ne couvre pas les chunks supprimés.

      time_bucket en LINQ

      Le provider Npgsql ne traduit pas time_bucket. Deux solutions : une requête SQL typée, ou une fonction mappée dans le modèle.

      Choix. SqlQuery convient pour une requête de reporting isolée. La fonction mappée convient quand le filtre ou la pagination se composent en LINQ. Dans les deux cas, filtrez sur m.Time, pas sur le bucket.

      Dernière valeur par série

      « La dernière mesure de chaque capteur » est une requête fréquente. Sa forme change beaucoup la performance.

      FormeExempleComportement
      LINQ GroupBy + FirstGroupBy(m => m.DeviceId).Select(g => g.OrderByDescending(x => x.Time).First())EF Core traduit en ROW_NUMBER() OVER (PARTITION BY ...). Le moteur lit toutes les lignes de la plage. Sans filtre de temps, il lit toute l'hypertable.
      DISTINCT ONSELECT DISTINCT ON (device_id) * ... ORDER BY device_id, time DESCCorrect avec un filtre de temps borné. Sans borne, le moteur parcourt beaucoup de chunks.
      last(value, time)SELECT device_id, last(value, time) ... GROUP BY device_idAgrégat Timescale. Lisible. Il lit aussi toutes les lignes de la plage.
      LATERAL + LIMIT 1Voir le code ci-dessousUn parcours d'index court par capteur. Le plus rapide avec une table devices et l'index (device_id, time DESC).

      Alternative. Pour un tableau de bord, une table latest_measurement mise à jour par upsert à l'insertion évite la requête. Un continuous aggregate avec last(value, time) par bucket est une autre option.

      Trous dans les données : time_bucket_gapfill

      Un capteur en panne n'envoie rien. time_bucket ne crée pas de ligne pour un bucket vide. Un graphique relie alors deux points éloignés.

      Règles

      • Le WHERE doit borner la colonne de temps des deux côtés. Sinon, la fonction ne connaît pas la plage à remplir.
      • locf : « last observation carried forward ». Usage : un état, un compteur.
      • interpolate : usage pour une grandeur continue, comme une température.

      Depuis .NET

      Utilisez SqlQuery<T> avec une propriété double? : un bucket vide donne NULL. Un type non nullable lève une exception à la lecture.

      Niveau 3

      Notions profondes

      Ces notions expliquent le fonctionnement interne : dimensionnement des chunks, moments de l'exclusion, format compressé, coût des écritures et des connexions.

      Simulateur : taille des chunks

      Règle de la documentation Timescale : les chunks actifs, index compris, doivent tenir dans environ 25 % de la mémoire. Les insertions modifient l'index du chunk récent. Si cet index sort du cache, chaque insertion lit le disque.

      Hypothèse : 150 octets par ligne, données et deux index compris. Rétention : 90 jours.

      Lignes par chunk

      Taille d'un chunk

      Budget (25 % RAM)

      Chunks sur 90 jours

      Part du budget

      Trop petit aussi est un problème. Chaque chunk est une table. Des milliers de chunks augmentent le temps de planification et le nombre de verrous par requête. Une requête sur 90 jours avec des chunks de 1 heure touche 2 160 tables.

      Exclusion de chunks : plan, démarrage, exécution

      TimescaleDB exclut les chunks à trois moments. Le moment dépend de la valeur connue dans le filtre. Le nœud Custom Scan (ChunkAppend) du plan fait l'exclusion au démarrage et à l'exécution.

      MomentValeur du filtreExempleVisible dans EXPLAIN
      PlanificationConstante, ou paramètre d'un plan personnalisétime > '2026-11-09'Les chunks exclus sont absents du plan.
      Démarrage de l'exécutionFonction stable : now(). Paramètre d'un plan générique.time > now() - INTERVAL '1 day'Chunks excluded during startup: 29
      ExécutionValeur venue d'une jointure ou d'une sous-requêteLATERAL, time > (SELECT ...)Chunks excluded during runtime: 29
      JamaisFonction appliquée à la colonne, ou type différentdate_trunc('day', time) = ...Tous les chunks sont dans le plan.

      Paramètres EF Core et plans génériques

      EF Core envoie les valeurs comme paramètres ($1). Avec des requêtes préparées, PostgreSQL passe à un plan générique après 5 exécutions si ce plan n'est pas plus cher. Le plan générique ne connaît pas la valeur : l'exclusion se fait au démarrage. Le résultat est correct, mais le plan liste tous les chunks.

      Pièges de type

      • timestamp comparé à timestamptz : la conversion dépend du fuseau de la session. Elle peut empêcher l'exclusion au planning.
      • DateTime avec Kind = Unspecified envoyé en timestamp sur une colonne timestamptz : conversion implicite.
      • Gardez le même type des deux côtés : timestamptz et DateTime UTC.

      Compression interne : du format ligne au format colonnes

      Type de colonneAlgorithmeEfficace quand

      FlottantGorilla (XOR avec la valeur précédente)Valeurs proches d'une mesure à la suivante

      Écrire dans un chunk compressé

      Les versions récentes acceptent INSERT, UPDATE et DELETE sur des chunks compressés. Le coût est différent d'un chunk normal.

      La ligne va d'abord dans une zone non compressée du chunk. Un job de compression la fusionne plus tard. Une contrainte unique oblige à décompresser les lots qui peuvent contenir un doublon.
      TimescaleDB décompresse les lots concernés, puis applique la modification. Un filtre sur segmentby limite les lots touchés. Sans ce filtre, tout le chunk peut être décompressé.
      Des mesures de J-10 arrivent en masse dans des chunks compressés. Chaque lot touché est décompressé. Le débit d'insertion baisse fortement.

      Conséquence pour EF Core. ExecuteUpdateAsync ou SaveChanges sur des mesures anciennes déclenche cette décompression. Réglez le délai de compression (compress_after) au-delà du retard maximal des données. Corrigez les données anciennes par des lots qui filtrent sur la colonne segmentby.

      Index par chunk et partitionnement spatial

      Un index créé sur l'hypertable est créé sur chaque chunk. Chaque index est donc petit. Mais chaque index ajouté coûte à chaque insertion.

      Index

      • Un CREATE INDEX sur l'hypertable prend un verrou sur chaque chunk. Pour une grande table, utilisez WITH (timescaledb.transaction_per_chunk).
      • Les chunks compressés n'utilisent pas les index B-tree des lignes. Ils utilisent segmentby et les métadonnées min/max de orderby.
      • Un index EF déclaré avec HasIndex devient un index de l'hypertable. La migration bloque l'écriture pendant la création.

      Partitionnement spatial

      Une deuxième dimension découpe chaque intervalle de temps en 4 chunks. La documentation la déconseille dans la plupart des cas. Elle est utile surtout pour répartir les données sur plusieurs tablespaces ou disques. Pour accélérer les filtres sur device_id, utilisez un index ou segmentby.

      COPY binaire et pooling Npgsql

      Le débit d'ingestion dépend du protocole, des allers-retours réseau et des connexions.

      MéthodeCe qui coûte
      SaveChangesChange tracker, détection des modifications, génération SQL. Les commandes partent en lots, mais chaque ligne est un INSERT avec ses paramètres.
      INSERT ... VALUES (...), (...)Une requête pour N lignes. Limite : 65 535 paramètres par requête dans le protocole PostgreSQL.
      INSERT ... SELECT * FROM unnest(@times, @ids, @values)Trois paramètres tableaux pour N lignes. Pas de limite de paramètres. Accepte ON CONFLICT.
      COPY ... FROM STDIN (FORMAT BINARY)Flux continu, pas d'analyse SQL par ligne, format binaire. Le plus rapide. Pas de ON CONFLICT.

      Pool de connexions

      • Npgsql garde un pool par chaîne de connexion. Valeur par défaut : 100 connexions au plus.
      • Chaque connexion PostgreSQL est un process côté serveur. 10 instances × 100 connexions dépassent souvent max_connections.
      • Un import COPY long garde sa connexion pendant tout l'import.

      Ingestion parallèle

      • Plusieurs COPY en parallèle augmentent le débit jusqu'à saturer le disque ou le CPU du serveur.
      • Lots conseillés : quelques milliers à quelques dizaines de milliers de lignes.
      • Les lignes d'un même lot dans le même chunk réduisent le nombre de chunks touchés.

      Tests avec Testcontainers

      SQLite ou le provider InMemory ne connaissent pas TimescaleDB. Testez sur une vraie instance dans un conteneur.

      À tester

      • La migration crée bien l'hypertable : SELECT * FROM timescaledb_information.hypertables.
      • Le mapping des dates : écriture et relecture d'un DateTime UTC.
      • Une requête sur le continuous aggregate après CALL refresh_continuous_aggregate(...).

      Policies et tests

      Les policies tournent en tâche de fond selon un planning. Un test ne doit pas attendre leur exécution. Appelez la fonction directement : compress_chunk, drop_chunks, refresh_continuous_aggregate.
