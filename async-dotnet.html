Niveau 1

Notions de base

Ces notions suffisent pour écrire du code async correct. Elles expliquent async, await et Task, et les erreurs fréquentes.

Trois notions à séparer

L'asynchronisme libère un thread. Le parallélisme utilise plusieurs threads.

I/O-bound

Asynchronisme

Le thread n'attend pas la fin d'une I/O. Pendant un appel à une base de données ou à une API HTTP, le thread retourne au ThreadPool. Outils : async, await, Task.

CPU-bound

Parallélisme

Plusieurs calculs s'exécutent en même temps sur plusieurs cœurs. Outils : Parallel, PLINQ, Task.Run hors serveur web.

Les deux

Concurrence

Plusieurs opérations sont en cours au même moment. Elles s'exécutent en même temps ou à tour de rôle.

À retenir. Une Task représente une opération. Une Task n'est pas un thread. L'instruction await ne bloque pas le thread. L'asynchronisme augmente le débit d'un serveur. Le parallélisme réduit la durée d'un calcul.

Le thread

Un thread exécute du code. Un thread ne possède pas les objets. Un thread n'est pas une Task. Un thread n'est pas un cœur.

Contenu d'un thread

  • Une pile. Elle contient les appels en cours et les variables locales. Taille réservée : 1 Mo sous Windows, 1,5 Mo sous Linux.
  • Un contexte CPU. Il contient les registres et l'adresse de l'instruction suivante.
  • Un stockage local. Il contient les valeurs [ThreadStatic] et ThreadLocal<T>.
  • Un objet noyau. Le système d'exploitation le gère. L'objet .NET Thread l'enveloppe.

Différences avec les autres concepts

  • Thread et cœur. 200 threads sur 8 cœurs : 8 threads s'exécutent. Les 192 autres attendent un cœur ou sont bloqués.
  • Thread et Task. Un thread exécute beaucoup de Tasks l'une après l'autre. Une Task d'I/O n'utilise pas de thread pendant l'attente.
  • Thread et objets. Les objets sont sur le heap. Tous les threads du process ont accès au heap.

États d'un thread

Le thread s'exécute sur un cœur.
Passe à Ready à la fin de sa tranche de temps.
Le thread est prêt. Il attend un cœur libre.
Passe à Running quand l'ordonnanceur le choisit.
Le thread attend une I/O, un verrou, .Result ou Thread.Sleep.
Passe à Ready à la fin de l'attente.

Thread bloqué. Un thread bloqué n'utilise pas le CPU. Mais il garde sa pile et ne fait pas d'autre travail. Dans le ThreadPool, chaque thread bloqué est un worker en moins pour les requêtes. Cette perte est la cause de la starvation.

Thread libéré : variables locales et services injectés

Les objets sont sur le heap. Le thread exécute seulement le code. Quand le thread retourne au ThreadPool, aucun objet n'est supprimé. Avancez étape par étape.

Les variables locales deviennent des champs

Au premier await qui suspend la méthode, .NET copie cette structure sur le heap. La Task en cours référence la continuation. La continuation référence la state machine. La state machine référence this. Pendant l'I/O, le GC ne supprime donc aucun de ces objets.

La DI ne crée pas de nouvel objet après await

La DI crée un objet pendant une résolution : création du contrôleur ou appel à GetRequiredService. La DI ne voit pas les await. Le scope DI appartient à la requête, pas au thread. Le scope existe jusqu'à la fin de la requête HTTP.

[ThreadStatic] et AsyncLocal<T>

Les objets restent disponibles après await. Les données stockées sur le thread posent un problème : identifiant de corrélation, utilisateur actuel, tenant. Dans cet exemple, deux requêtes A et B partagent les workers T4 et T7.

Fonctionnement

AsyncLocal stocke la valeur dans l'ExecutionContext. À chaque await, .NET capture l'ExecutionContext. À la reprise, .NET restaure l'ExecutionContext sur le worker qui reprend. La valeur suit donc le flux logique, pas le thread.

L'ExecutionContext est copié à chaque modification. Une méthode appelée qui change une valeur ne change pas la valeur de l'appelant.

Utilisations dans le framework. IHttpContextAccessor.HttpContext, Activity.Current (trace OpenTelemetry ou Datadog), ILogger.BeginScope et CultureInfo.CurrentCulture utilisent ce mécanisme.

ConfigureAwait : position de la continuation

ConfigureAwait(bool continueOnCapturedContext) indique où exécuter la continuation. Valeur par défaut : true. Dans ce cas, await capture SynchronizationContext.Current et y envoie la continuation.

À retenir. Utilisez ConfigureAwait(false) dans les bibliothèques. Dans le code d'une application ASP.NET Core, il n'a pas d'effet. Il ne change jamais l'ExecutionContext. Il agit seulement quand await suspend la méthode. En UI, après une suspension avec ConfigureAwait(false), l'accès à un contrôle provoque une exception.

async void : raisons de l'éviter

Une méthode async void ne retourne pas de Task. L'appelant ne peut pas l'attendre. L'appelant ne connaît pas sa fin. Une exception arrête le process.

Conversions implicites dangereuses

Une lambda async passée à un paramètre Action devient async void. Le compilateur ne donne pas d'avertissement. Il choisit Func<Task> seulement si une surcharge l'accepte.

Seul cas accepté : l'event handler

Un délégué EventHandler impose le type de retour void. Dans ce cas, mettez le try/catch dans la méthode. C'est le seul endroit où le code peut recevoir l'exception.

Erreur intermittente. Si l'opération se termine avant Dispose, le code fonctionne. Exemples : cache, réponse très rapide. L'erreur apparaît donc en production et pas en local.

Autres effets, même sans using

  • Un try/catch dans la méthode ne reçoit pas les erreurs async. L'exception arrive plus tard, chez l'appelant.
  • La méthode n'apparaît pas dans la stack trace async. Le diagnostic est plus difficile.
  • Une erreur de validation d'argument se produit immédiatement à l'appel. Elle n'est pas stockée dans la Task.

Task et ValueTask

Une Task est un objet sur le heap. Chaque appel à une méthode async crée donc une allocation. ValueTask évite cette allocation quand le résultat est déjà disponible.

Contenu de la struct

Une ValueTask est une petite struct. Son champ _obj indique lequel des trois cas s'applique.

Cas_objExemple
1. Résultat déjà disponiblenull. La valeur est dans _result.Le cache : ValueTask.FromResult(user)
2. Enveloppe une TaskUne Task<T>Le chemin lent : new ValueTask<User>(LoadUserAsync(id))
3. Source réutilisableUn IValueTaskSource<T>Socket.ReceiveAsync, Channel.Reader.ReadAsync

IValueTaskSource est une interface. Elle offre les mêmes services qu'une Task : un état, une continuation, un résultat. Une Task terminée reste terminée pour toujours. Un IValueTaskSource se remet à zéro après la lecture du résultat et sert à l'opération suivante. Il n'y a aucune allocation, même pour une vraie opération asynchrone. Ces sources sont internes au framework : vous ne les écrivez presque jamais.

Règle : une seule consommation. Une ValueTask peut utiliser un objet réutilisé (IValueTaskSource). Après le premier await, cet objet peut servir à une autre opération. Un deuxième await, un .Result ou un WhenAll sur la même ValueTask donne un comportement indéfini : mauvais résultat, exception ou blocage.

Image : un ticket de vestiaire

Une Task est un reçu. Vous pouvez le relire autant de fois que vous voulez. Une ValueTask est un ticket de vestiaire. Le ticket en papier est la struct : il est copié puis jeté. Le crochet est l'objet réutilisé sur le heap. Après la remise du manteau, le crochet sert au client suivant. Un deuxième passage avec le même ticket donne une erreur, ou le manteau d'un autre client.

Le thread dans le système

Changement de contexte

L'ordonnanceur remplace parfois le thread d'un cœur par un autre thread. Il enregistre les registres de l'ancien thread. Il charge les registres du nouveau thread. Cette opération dure environ une microseconde.

Le coût indirect est plus grand. Les caches du cœur contiennent les données de l'ancien thread. Le nouveau thread commence donc avec des caches inutiles. Plus de threads actifs que de cœurs donne plus de changements de contexte et moins de travail utile.

Raison de l'injection lente

Le ThreadPool suppose un travail court et non bloquant. Un worker par travail en attente donnerait des milliers de threads pendant un pic de charge. Ces threads utiliseraient beaucoup de mémoire et de changements de contexte. Le ThreadPool fait donc attendre le travail. Cette règle est efficace avec du code async. Elle est mauvaise avec du code bloquant.

Cœurs logiques et cœurs physiques. ProcessorCount compte les cœurs logiques. Avec l'hyperthreading, un cœur physique donne deux cœurs logiques. Ces deux cœurs logiques partagent les unités de calcul. Le gain est de 15 à 30 % sur un calcul, pas de 100 %.

Simulateur : files locales et vol de travail

Le ThreadPool a 4 workers. Une requête HTTP arrive dans la file globale. Au démarrage, chaque requête crée 2 tâches. Ces tâches vont dans la file locale du worker. Un worker libre cherche du travail dans cet ordre : sa file locale (LIFO), la file globale (FIFO), la file d'un autre worker (vol, FIFO).

LIFO dans la file locale. La tâche la plus récente utilise souvent les données que le worker vient de lire. Ces données sont encore dans le cache du cœur.

Vol par l'autre extrémité. Le voleur et le propriétaire ne prennent pas la même tâche. Ils n'ont presque jamais besoin de verrou.

Image : une cuisine de restaurant

Les commandes des clients arrivent au passe. Chaque cuisinier a sa pile de préparations sur son plan de travail. Il finit d'abord ce qu'il vient de lancer. Quand son plan est vide, il va au passe. Si le passe est vide, il va chez un collègue débordé. Il prend une préparation en bas de la pile du collègue, sans le gêner.

L'endpoint lit une commande en base, appelle deux API et calcule le prix de chaque ligne. Log affiche le thread de chaque étape.

Les 4 calculs de 100 ms durent environ 200 ms au lieu de 400. Sans le vol, W2 ferait les 4 calculs seul pendant que W1 et W4 attendent. L'ordre d'exécution n'est pas l'ordre de création : ne comptez jamais sur l'ordre des Task.Run.

Remplacez ② par un appel synchrone (First(...) ou FirstAsync(...).Result). W1 reste bloqué pendant la requête SQL. Avec 200 requêtes simultanées, tous les workers sont bloqués. Les nouvelles requêtes restent dans la file globale. Le pool ajoute des threads lentement. C'est la starvation.

Task.Run dans un endpoint. Utilisez-le seulement pour découper un vrai calcul CPU en plusieurs morceaux, comme au ⑥. Un seul await Task.Run(...) libère un worker pour en occuper un autre : aucun gain. Pour une I/O, await suffit.

Injection de threads, conteneurs et SetMinThreads

Ce graphique montre le temps nécessaire pour donner un worker à chaque requête bloquée. Modèle simplifié : création immédiate jusqu'au minimum, puis 1 worker toutes les 500 ms.

Conteneur Kubernetes

Un nœud Kubernetes est une machine. Plusieurs pods partagent ses cœurs. resources.limits.cpu fixe la part maximale d'un conteneur.

ValeurSignification
1000m ou 11 cœur complet
500mLa moitié d'un cœur
100m10 % d'un cœur
2500m2,5 cœurs

L'unité est le millicœur (m) : 1000m = 1 cœur. La limite est un temps de calcul, pas un nombre de cœurs. Linux découpe le temps en tranches de 100 ms. Avec 100m, le conteneur a droit à 10 ms de CPU par tranche, tous threads confondus. Quand il a tout consommé, Linux le met en pause jusqu'à la tranche suivante. C'est le throttling : la latence augmente, alors que le graphe CPU paraît calme.

.NET lit la limite CPU du conteneur. Il arrondit cette limite à l'entier supérieur, avec un minimum de 1. Le résultat donne ProcessorCount, donc le minimum de workers.

async void : code généré

Le compilateur transforme chaque méthode async en state machine et en builder. Le type de retour choisit le builder. Cette différence explique tous les problèmes d'async void.

Raison de l'erreur CS4008 avec await Save()

Le compilateur transforme await x en appels à x.GetAwaiter(), IsCompleted, OnCompleted(continuation) et GetResult(). Il faut donc un objet qui représente l'opération. Une méthode void ne retourne pas d'objet. Le compilateur signale donc error CS4008: Cannot await 'void'. AsyncVoidMethodBuilder ne donne pas non plus de Task en interne.

Comportement de chaque builder

AppelAsyncTaskMethodBuilderAsyncVoidMethodBuilder
Create()Prépare une Task.Capture SynchronizationContext.Current. Appelle OperationStarted() si le contexte existe.
SetResult()La Task passe à RanToCompletion. Les continuations démarrent.Appelle OperationCompleted() si le contexte existe. Sinon, aucune action.
SetException(e)L'exception est stockée dans la Task. await la relance.Aucune Task ne peut stocker l'exception. Le builder relance l'exception sur un autre thread.

OperationStarted et OperationCompleted. Ces appels sont le seul suivi possible d'un async void. Ils passent par le SynchronizationContext. ASP.NET sur .NET Framework comptait ainsi les opérations en cours. xUnit utilise ce mécanisme pour attendre un test async void. ASP.NET Core et les applications console n'ont pas de contexte : il n'y a aucun suivi.
